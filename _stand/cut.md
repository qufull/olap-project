# Договор об ограничениях проекта (`cut.md`)

Ниже зафиксирован список архитектурных элементов и детализаций данных, которые **сознательно исключены** из контура проекта в текущем семестре, а также последствия этих решений для аналитических отчётов.

## 1. Нет попозиционной детализации чека (Order Items / Блюда)
* **Решение:** Гранулярность таблицы `fact_orders` зафиксирована на уровне всего заказа (`order_id`), без дочерней таблицы `fact_order_items` и справочника блюд `dim_menu_items`.
* **Чем это грозит отчётам:**
  * Мы не можем считать маржинальность отдельных блюд, делать ABC/XYZ-анализ меню или находить «товары-локомотивы» (Market Basket Analysis).
  * Тип кухни (`cuisine`) определяется целиком по ресторану из `dim_restaurants`, поэтому для мультикухонных ресторанов вся сумма заказа целиком относится к основной кухне заведения.

## 2. Нет потоковой загрузки в реальном времени (Kafka / CDC / Streaming)
* **Решение:** Данные загружаются пакетно (Batch-генерация CSV -> аналитическая витрина в DuckDB). Отказываемся от брокеров сообщений (Kafka/RabbitMQ) и потоковых конвейеров.
* **Чем это грозит отчётам:**
  * Витрина предназначена для исторической OLAP-аналитики (T+1), а не для оперативного диспетчерского мониторинга «где прямо сейчас едет курьер».
  * В `fact_orders` хранится только финальный статус заказа (`Доставлен`, `Отменен`, `Опоздание`), без промежуточных временны́х меток (`created_at -> cooked_at -> picked_up_at -> delivered_at`). Из-за этого при опоздании (> 60 мин) по отчёту нельзя разделить вину между долгой готовкой ресторана и медленной ездой курьера.

## 3. Нет геопространственной аналитики (PostGIS / полигоны зон доставки / GPS-треки)
* **Решение:** Не храним координаты ресторанов и клиентов (`lat`/`lon`), полигоны районов и реальные километражи маршрутов.
* **Чем это грозит отчётам:**
  * Время доставки (`delivery_time_minutes`) анализируется только в разрезе типа транспорта курьера (`vehicle_type`) и времени суток, без поправки на реальное расстояние в километрах и погодные пробки в конкретном районе города.

## 4. Нет распределённого кластера (ClickHouse Cluster / Spark / Airflow)
* **Решение:** Вся обработка 1 000 000 строк выполняется локально на одном узле внутри колоночной СУБД **DuckDB** (in-process OLAP).
* **Чем это грозит отчётам:**
  * На объёме 1–10 млн строк DuckDB отрабатывает запросы за доли секунды на одном ноутбуке, однако архитектура не предусматривает горизонтального шардирования и параллельной записи от десятков внешних сервисов.

## 5. Нет учёта промокодов, чаевых и комиссий агрегатора (Финансовая детализация)
* **Решение:** В таблице фактов хранится единая сумма заказа `total_amount`.
* **Чем это грозит отчётам:**
  * В отчётах `total_amount` трактуется как полная стоимость заказа (GMV). Если бы бизнесу потребовалось считать чистую комиссионную выручку платформы (Take Rate), стоимость доставки для клиента или бюджет на скидки по промокодам, текущая витрина завышала бы реальную выручку на размер скидок.
